# خطة تطوير Superior

آخر تحديث للخطة: 2026-11-02. هذه خطة تنفيذ وقبول، وليست إعلان اكتمال أو نتائج أداء.
يُنتج المشروع `Superior.exe` لويندوز 10/11. الاختبارات والبناء عبر GitHub Actions
فقط، ولا يُجرى بناء محلي في هذه الجلسة.

## الهدف وحدود الادّعاءات

تحسين صورة نافذة اللعبة وتوليد إطارات بكلفة قابلة للقياس، مع أولوية الراحة
واستمرار اللعبة دون تدخل في عمليتها. لا حقن، لا hooks، لا تعديل تلقائي لإعدادات
النظام أو سقف FPS. هذا لا يضمن قبول كل أنظمة مكافحة الغش.

- نجاح CI يعني نجاح البناء واختبارات المنطق، وليس نجاح تجربة GPU.
- نسبة 99% هدف لمجموعة مرجعية موثقة، وليست ضماناً لكل لعبة أو بديلاً عن الحقيقة المرجعية.
- لا يُسمّى الزمن الجداري للاستدلال «زمن GPU»، ولا نتيجة proxy «جودة مؤكدة».
- لا تُفَعّل ميزة غير منفذة بزر شكلي، ولا تُملأ القياسات المفقودة بأرقام افتراضية.
- LCD لا يتحول إلى OLED حقيقي؛ لا توجد بيانات عمق أو متجهات حركة من اللعبة.

## الأولوية 0 — تثبيت القياس قبل زيادة التعقيد

### الدفعة السابقة — منفذة، واختبار الواجهة يدوياً ما زال مطلوباً

1. تشغيل التحقق المرجعي من الواجهة باختيار manifest ومكان التقرير.
2. عامل CPU واحد بأولوية منخفضة، تقدم قابل للعرض، وإلغاء تعاوني.
3. منع تزامن التحقق مع الالتقاط، وانتظار إيقاف العامل قبل إنهاء البرنامج.
4. إزالة خرائط الحواف كاملة الحجم من RAM؛ حسابها أثناء المرور على البكسلات.
5. حد 16,777,216 بكسل للصورة، مع أقصى بُعد 8192، قبل التخصيص.
6. تقرير لكل `content_class` كما يحدده ملف الاختبار، دون مصنّف مزعوم.
7. `baseline_percent` اختياري يمنع قبول نتيجة أدنى من خط أساس موثق.
8. اختبارات للإلغاء، التقدم، تراجع baseline، الأصناف وحد الذاكرة.

**معيار القبول:** CI أخضر؛ لا نجاح عند الإلغاء؛ لا نسبة جزئية تُعرض كنهائية؛
إمكانية تغيير اللغة وتحريك النافذة أثناء العمل؛ الإغلاق يلغي العامل دون وصول إلى
واجهة محررة. الذاكرة المحجوزة لأربع صور float بحدها الأعلى نحو 256 MiB دون
خرائط حواف كاملة؛ هذا حساب تخصيص وليس قياساً للعملية كلها.

**اختبار يدوي:** ملف متعدد الصور، ثم إلغاء أثناء القراءة/الحساب، والإخفاء للشريط،
والخروج أثناء الاختيار والعمل. اختبر تعارض مسارات التقارير والمدخلات والعربية.

### التالي بعد هذه الدفعة

- مسجل مقاطع اختبار عالي المعدل منفصل عن المسار الساخن، مع حدود مدة/حجم/قرص.
- ربط إعادة التشغيل offline بمحرك shader نفسه، لا بدالة تقريبية مختلفة.
- إرفاق هوية مجموعة البيانات ونسخة البرنامج والإعدادات بكل baseline.
- مقاطع تضم حوافاً رفيعة، HUD، نصوصاً، قطع مشاهد، حجباً وحركة سريعة.
- مقارنة baseline فقط عند تطابق مجموعة البيانات وإعدادات القياس؛ لا خفض تلقائي له.

## الأولوية 1 — استقرار العرض والراحة

### الدفعة الحالية: رصد الجلسة قبل تحسين الجدولة

- عدادات مستقلة لمسار الإطار الحقيقي والمسار المولد: المجدول، نجاح S_OK،
  المحجوب، الحالات الأخرى، الفاشل، الملغى والمعلّق.
- فصل أسباب الإلغاء: وصول زوج جديد، توقف مؤقت، تغيير حجم المصدر، وإيقاف الجلسة.
- حساب زمن النشاط والتوقف المؤقت، وعدم مد فواصل استدعاءات العرض عبر فترة توقف.
- قياس زمني جداري حول الرسم واستدعاء Present، وتأخر بدء المعالجة عن موعدها.
- عرض اللقطة في الواجهة وتصدير JSON؛ لا نسخ لإطارات GPU ولا بيانات صور في التقرير.
- إبقاء `scanout_fps` ونسبة النجاح المرجعية غير متاحتين بدلاً من اختلاقهما.
- إصلاح تلميح شريط النظام كي لا يصف كل مضاعف بأنه x2.

**معيار القبول الآلي:** حفظ المعادلة `scheduled = submitted + occluded +
other + failed + discarded + pending` لكل مسار، وصحة أزمنة pause/stop/restart،
ورفض تقرير غير متسق. تعاد اختبارات CPU وأوامر offline عبر Actions.

**ما يلزم يدوياً:** مقارنة العدادات مع سجل الجهاز، إلغاء أعمال معلقة بالتصغير
وتغيير الحجم والوصول السريع للصور، تصدير تقرير أثناء جلسة/بعد إيقافها، وإغلاق
البرنامج أثناء نافذة الحفظ. نجاح S_OK ليس scan-out، ومسار generated قد يستخدم
fallback داخل shader؛ لا يستنتج منه عدد إطارات سليمة بصرياً.

### الأعمال التالية في الاستقرار

1. استخدام عدادات هذه الدفعة لقياس أثر إسقاط الأعمال وسياسة استبدال الطابور؛ اختبار scan-out يحتاج أدوات/عتاد منفصلين.
2. قياس مجموع GPU لكل فترة خرج؛ ربط العينات بالمراحل والجلسة الصحيحة.
3. إصلاح الاسترداد من device lost، وإبطال التاريخ عند تغير الحجم/DPI/الشاشة.
4. كشف GPU الذي يقود الشاشة والتحذير من النسخ العابر للمحولات؛ لا تخمين GPU اللعبة.
5. ميزانية تخصيص فعلية للملمس والمخازن، ثم pools وتقليص استباقي.
6. معايرة قابلة للإلغاء، بمفتاح GPU/driver، تتضمن سبب كل تخفيض.

**القبول:** لا نمو مستمر للمقابض/الذاكرة عبر 100 بدء/إيقاف؛ استرداد بعد فشل جهاز
محقون في واجهة اختبار؛ لا تذبذب governor عند تغير الحمل؛ توثيق hardware run
على iGPU ونظام هجين وجهاز منفصل. لا يُضمن حد 25% قبل قياس الإجمالي.

## الأولوية 2 — تدفق وتوليد أكثر موثوقية

1. pyramid من الصور وتدفق منخفض الدقة، ثم refinement تحت البكسل.
2. confidence وocclusion/disocclusion واضحة مع رفض التدفق غير المتسق.
3. حماية HUD والنصوص: أقنعة يدوية أولاً، ثم كشف آلي مقاس.
4. ملء الحجب من المصدر المناسب بدلاً من فرض cross-fade على كل فشل.
5. تحقق من pacing عند x2/x3/x4؛ التخفيض عند فشل الميزانية أو الثقة.
6. debug views للتدفق والثقة والحجب، مع أرقام فعلية لا مؤثرات شكلية.

**القبول:** مقارنة بمحرك الإصدار السابق على نفس المقاطع، تقرير للمكسب والخسارة
والزمن والذاكرة. تُرفض الإعدادات التي تخفّض الجودة خارج العتبة المتفق عليها.
المراحل الأعلى رتبة وNVOFA اختيارية بعد إثبات المسار العام.

## الأولوية 3 — تراكم زمني ورفع عصبي مباشر

1. إعادة إسقاط التاريخ عالي الدقة بالتدفق المشترك، مع clamping ورفض الحجب.
2. فصل النص/HUD عن التاريخ والهلوسة العصبية.
3. اختيار نموذج خفيف، مراجعة ترخيصه ومصدره، والتحقق من hash وواجهته.
4. D3D11/D3D12/DirectML interop ومزامنة fences دون نسخ إطارات إلى CPU في اللعب.
5. tiles بتداخل وتخطيط VRAM وإلغاء cache على القطع وتغير الحجم.
6. قياس كلفة النموذج وجودته قبل السماح به؛ Comfort يبقى دون neural افتراضياً.
7. FP16/INT8 والكادنس التكيفي فقط إن أثبتت المقارنة فائدتها.

**القبول:** النموذج المفقود/التالف/غير المدعوم لا يعطّل البديل المكاني؛ لا seam بين
البلاطات؛ تقرير A/B مقابل الرفع المكاني؛ قياس متواصل على عتاد DX12 فعلي.
الأمر العصبي offline الحالي ليس إثباتاً لاكتمال هذه المرحلة.

## الأولوية 4 — validator وهدف 99%

- تعريف S/E/F ثابت داخل كل مجموعة اختبار ومذكور في تقريرها.
- عدم احتساب الإطارات الناقصة/الفاشلة كإطارات ناجحة أو حذفها لرفع النسبة.
- تقرير حسب نوع المحتوى ومستوى الجودة؛ فصل synthetic عن ألعاب حقيقية.
- proxy حي رخيص على GPU لكل إطار مولد، مع fallback وعدادات واضحة.
- state machine تخفّض القوة ثم المضاعف ثم تعطل التوليد عند تدهور مستمر.
- لا يُعلَن تحقيق 99% إلا للمجموعة والإصدار والإعدادات المقاسة بالضبط.

**القبول:** تقارير قابلة لإعادة الإنتاج؛ فشل CI عند تراجع corpus القياسي؛ اختبار
يدوي للتشبح على أجهزة المستخدم، وليس على المقاييس وحدها.

## الأولوية 5 — قبول وتوزيع

- مراجعة /W4 وفحوص ساكنة وتثبيت dependencies بالـhash.
- اختبار Windows 10/11، Intel/AMD/NVIDIA، بطارية وشاحن، وشاشات بترددات مختلفة.
- فحص العربية: اتصال الحروف، لام ألف، التشكيل، مزج الأرقام والمسارات، DPI وتكبير النص.
- onboarding وشرح borderless واختيار الوضع والقياس قبل التفعيل.
- إصدار portable مع notices وSHA256؛ installer/release workflow وتوقيع عند توفر شهادة.
- لا رفع تقارير أو مقاطع من جهاز المستخدم دون اختيار صريح؛ التقارير محلية افتراضياً.

## دورة التسليم لكل دفعة

1. تحديث الخطة بحالة التنفيذ وحدودها ومعيار قبول محدد.
2. تنفيذ وحدة متكاملة واختبارات منطقها، لا أسماء وحدات فارغة.
3. رفع إلى فرع الجلسة الحالي فقط وتشغيل Actions؛ لا دمج إلى main دون طلب.
4. إصلاح أي بناء أحمر قبل التسليم، وتقديم رابط artifact الصحيح.
5. تقرير: المنفذ، المتحقق منه آلياً، ما يحتاج GPU، والمشكلات المعروفة.
6. لا يُشترط GPU لإجراء اختبارات CPU؛ لا تُشغّل اختبارات GPU الوهمية في CI.

## توسعة المنتج — الدفعة الأولى (2026-11-02)

- دليل إعداد عربي/إنجليزي داخل الواجهة: تجهيز اللعبة، البدء، المقارنة، الإحصاءات واستكشاف الأخطاء.
- عرض حالة تهيئة DX11 ووجود بيانات ميزانية الذاكرة والوضع الآمن فقط؛ ليس اختبار توافق WGC أو قياس أداء.
- نقل إعدادات الصورة والجلسة بحزمة JSON محددة الإصدار، دون نقل اللغة أو الاختصارات أو تفضيل الملفات التلقائية.
- منع النقل أثناء الالتقاط والأدوات، استخدام نافذة ملفات أصلية وحفظ ذري، حد قراءة 64 KiB وحد تعشيق.
- رفض الملفات الناقصة أو الأنواع غير الصحيحة أو الإصدارات غير المعروفة دون تعديل الإعدادات.
- اختبارات CPU للحزمة والحدود وحفظ التفضيلات المحلية؛ البناء عبر Actions فقط.

يبقى مطلوباً يدوياً: تجربة النقل بين جهازين، مسار عربي، إلغاء نوافذ الملفات والخروج أثناء فتحها،
وتخطيط الدليل عند DPI مختلف. لا يشمل هذا استرداد فقد جهاز الرسوم أو LUT أو تحسيناً عصبياً حياً.
الحجم ميزانية وليس هدفاً للحشو؛ لا ادعاء أن هذه الدفعة تصل إلى 20–50 ميجابايت.
